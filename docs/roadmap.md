# 产品版本路线图

本路线图先交付可运行的程序基础，再按用户能力划分版本：每个小版本只回答一个主要问题，并交付可实际使用和验收的能力。远期版本表示能力方向，不预先锁定实现细节或交付日期。

## 1. 大版本划分

| 大版本 | 阶段 | 核心问题 | 主要交付 |
| --- | --- | --- | --- |
| v0.x | 程序基础、交易采集与信号输出 | 服务如何运行，这个账户在交易什么？ | HTTP 服务与配置、成交查询、持续监控、标准成交事件、跟单候选信号 |
| v1.x | 账户分析 | 这个账户赚了多少，承担了多大风险？ | 账户状态、资金流水、收益、交易指标和风险变化 |
| v2.x | 账户筛选与评价 | 哪些账户值得关注，为什么？ | 账户比较、条件筛选、策略特征和综合评价 |
| v3.x | 跟单验证与执行 | 是否跟随、跟多少、如何执行，效果怎样？ | 模拟跟单、执行验证、受限实盘和跟单管理 |
| v4.x | 历史重建与扩展 | 能还原指定时点并分析更早的历史吗？ | 事件回放、区间重算、历史补充来源 |
| v5.x | 多链与多协议扩展 | 同一地址在不同链和协议上的整体表现怎样？ | 新来源接入、独立建账、地址级聚合 |
| v6.x | 数据完整审核 | 数据是否完整、准确，异常如何修复？ | 独立异步复核、多来源对账、修正与修复闭环 |
| v7.x | 钱包扩展 | 能选择自己的签名或托管方式吗？ | 本地签名器、MPC 和第三方托管钱包适配 |

每个阶段的 `.0` 是该阶段第一个可用的最小版本，后续小版本逐步完善。大版本号表示能力归属，不要求各阶段严格串行开发。

README 定义产品最终目标，本路线图安排其逐步交付顺序。前四个阶段构成产品主线，后续独立大版本承接历史重建、多链扩展、完整审核和钱包扩展。Hyperliquid 是首个支持的协议，后续扩展不改变统一账户事实和服务职责。

## 2. v0.x：程序基础、交易采集与信号输出

阶段目标：先建立可配置、可响应 HTTP 请求的运行程序，再在同一工程和架构中逐步加入成交查询、持续采集和可追溯的跟单候选信号。

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v0.0 程序基础 | 程序能否按配置启动并响应 HTTP 请求？ | 通过 Docker Compose 启动 query-api 容器，通过配置文件设置监听地址、端口和日志级别，通过 HTTP 查询健康状态及程序版本 | 镜像构建、配置挂载、端口映射和容器启停通过；配置加载与校验通过；健康及版本接口返回约定的状态码和 JSON；配置错误或端口占用时明确启动失败；请求和错误有日志；支持优雅退出；工程结构与设计文档一致 |
| v0.1 查询成交 | 这个地址最近交易了什么？ | 通过 HTTP 请求提交一个 Hyperliquid 地址，查看近期合约成交 | 实际地址与来源记录核对通过；保留来源响应；显示查询范围、无成交和失败状态 |
| v0.2 保存成交 | 已查询的成交能保留下来吗？ | 成交持久化，按时间查询 | 稳定成交 ID；原始响应与成交记录分别保存并关联，可重新解析；重复拉取不重复入账；重启后记录保留 |
| v0.3 自动更新 | 能不用手动查询吗？ | 定时拉取一个地址的新成交，查看更新状态 | 保存采集水位；重启后继续；失败和最后成功时间可见 |
| v0.4 实时监控 | 能及时发现新成交吗？ | 实时接收成交，断线后恢复 | HTTP 与 WebSocket 去重；在来源可查询范围内补齐断线缺口；覆盖不足明确披露 |
| v0.5 信号输出 | 新成交能供其他系统跟随吗？ | 标准化成交，向一个 webhook 输出跟单候选信号 | 区分历史回补与实时成交；主动已成交操作才产生候选信号，清算、强制减仓、结算不可跟单；标准事件存储后发布，不等待分析或全面审核；记录成交、接收与发布时间；事件身份和来源可追溯；至少一次投递，接收方可去重和判断时效 |
| v0.6 多地址监控 | 能同时观察几个地址吗？ | 添加、暂停和恢复监控地址，分别查看状态 | 单地址异常不影响其他地址；数量限制明确；暂停恢复后的覆盖和信号边界明确 |
| v0.7 现货成交与信号 | 现货交易也能观察和输出吗？ | 查看现货成交，输出主动现货买卖候选信号 | 正确识别市场、资产及手续费；合约与现货分别筛选；实际记录核对通过 |

v0.0 是后续所有版本的程序基础：落实 Rust workspace、配置加载、HTTP 路由、统一响应与错误处理、基础日志和程序生命周期。HTTP 入口位于详细设计的 `gateway/query-api`，配置位于 `config/`；后续业务逻辑按设计归属相应服务，通过接口接入 HTTP 入口。首版使用 Docker Compose 启动一个 query-api 容器，后续按需加入其他独立进程对应的容器，不要求提前部署所有服务或引入数据库和消息系统。

后续版本在这套工程结构、运行方式和配置机制上迭代。HTTP handler 负责请求与响应，业务逻辑与协议适配分别位于设计指定模块，避免将成交获取、解析和计算写进路由。配置项按实际功能逐步扩展并保持明确的兼容规则；新增后台任务或拆分进程时复用已有业务模块和运行约定。

v0.x 保存和发布标准成交事件：对分析服务是交易记录，其中主动成交对跟单服务是候选信号。原始数据保留来源与可用位置标识，查询逐步支持账户、时间及适用的区块范围。候选信号表示可以进入跟单规则判断，不表示推荐交易或必须执行。跟随金额、用户规则、风险限制和钱包执行归属 v3.x。

## 3. v1.x：账户分析

阶段目标：从交易流水走向可解释的账户状态、收益和风险分析。

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v1.0 当前账户概览 | 账户现在持有什么、价值多少？ | 查看合约持仓、现货余额、账户价值及官方提供的盈亏字段 | 与官方状态核对；展示快照时间、来源和口径；账户快照作为后续观察期初始基准 |
| v1.1 账户变化历史 | 开始观察后，账户如何变化？ | 查询定期保存的账户价值、持仓、余额和市场价格快照 | 只展示实际保存的历史；估值关联价格与时间；缺失区间和采样精度可见 |
| v1.2 资金流水 | 价值变化里哪些来自资金进出？ | 采集、查询并持续发布充值、提现、划转、资金费、清算、奖励及其他账户账本事实 | 事实按确定顺序建账，关联原始数据；区分外部资金流和内部划转；费用不重复计算；资金账本事实及强制事件不触发普通跟单 |
| v1.3 观察期净收益 | 观察期间实际赚了多少？ | 按区间计算净收益金额，并解释价值变化与资金进出 | 按期末价值减期初价值再减外部净流入计算；内部划转不重复计入；估值价格和计算版本可追溯；覆盖不足时标记不完整或无法计算 |
| v1.4 合约交易过程 | 一次合约交易如何从开仓到平仓？ | 归并开仓、加仓、减仓、平仓和反转，计算持仓成本、已实现及未实现盈亏 | 净持仓从零到零形成完整周期，进行中持仓单独展示；期初持仓以可靠市场价格建立估算成本，仅代表观察期盈亏；费用、价格及计算版本可追溯 |
| v1.5 现货成本与盈亏 | 卖出现货赚了多少，剩余成本多少？ | 按移动加权平均成本计算库存，按逻辑卖出操作计算已实现盈亏，并估值未实现盈亏 | 以交易对基础资产分析，计价资产不重复算作另一笔交易；手工案例核对；期初成本估算、资产转入转出和费用处理明确 |
| v1.6 基础交易指标 | 账户交易表现怎样？ | 查看账户价值、净盈亏、成交量、成交笔数、完整交易次数、胜率、盈亏比和持仓周期 | 合约完整周期从零到零，进行中持仓不计胜率；现货按逻辑卖出统计；交易次数及胜率分类展示，其余可统一计价汇总；披露样本量、覆盖和估算占比 |
| v1.7 收益与风险曲线 | 盈利是否稳定，风险有多大？ | 查看收益率、回撤、仓位集中度及杠杆变化 | 收益率与杠杆口径明确；采样精度和数据缺口可见 |

历史快照查询在 v1.1 交付。指定时点的事件回放和重算归属 v4.x，多链和多协议账户归属 v5.x；v1.x 先完成 Hyperliquid 观察期内的账户分析。

## 4. v2.x：账户筛选与评价

阶段目标：帮助用户找到符合要求的账户，并解释比较和评价依据。

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v2.0 账户比较 | 关注的账户中，哪些表现更好？ | 在统一观察周期下比较收益、回撤和交易活跃度 | 展示覆盖范围、样本量和估算比例；不同口径不直接混排 |
| v2.1 条件筛选 | 哪些账户符合我的要求？ | 按收益、回撤、交易次数和持仓周期等筛选，保存条件 | 每个结果都能解释入选原因；数据不足时明确处理 |
| v2.2 策略特征 | 账户主要采用什么交易方式？ | 查看标的偏好、方向偏好、频率和持仓周期特征 | 特征有数据依据；样本不足不作确定判断 |
| v2.3 综合评价 | 多维度下应优先研究谁？ | 调整权重，查看综合评分和各项贡献 | 权重、评分口径和计算版本可见；结果可追溯到指标 |

错误可见、数据可追溯和基础校验是所有版本的要求。系统化独立审核归属 v6.x。现有多维权重方案可作为 v2.3 的候选设计，在基础指标经过使用验证后再确定。

## 5. v3.x：跟单验证与执行

阶段目标：消费 v0.x 的候选信号，逐步验证规则、执行流程和实际效果。

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v3.0 模拟跟单决策 | 按我的规则，这笔交易会不会跟？ | 配置目标、标的、金额及限制，记录模拟决策 | 每笔信号有执行或忽略原因；重复及过期信号不重复决策 |
| v3.1 模拟跟单表现 | 按这些规则跟随，效果可能怎样？ | 记录模拟成交、仓位、费用及盈亏，与目标比较 | 成交价格、延迟和滑点假设明确；结果可复算 |
| v3.2 测试环境执行 | 信号到下单的流程能跑通吗？ | 在测试环境完成规则判断、签名、提交和成交追踪 | 通过统一钱包接口接入首个签名器；区分签名并发送与仅签名后提交；保存请求标识；超时、拒单、部分成交和重启恢复不导致重复下单 |
| v3.3 受限实盘跟单 | 能在明确限制下实际跟随吗？ | 使用金额和持仓限制执行跟单，支持暂停及停止 | 本地签名通过 KMS/HSM 或专用密钥服务保护密钥，外部钱包仅保存引用；凭证不进入日志；真实执行可追溯；停止机制、异常恢复和结果核对完成验收 |
| v3.4 跟单管理 | 能长期管理多组跟单关系吗？ | 管理多目标、资金分配、规则调整及实际表现 | 规则变更边界明确；信号、决策、订单和成交完整关联 |

## 6. 后续独立大版本

后续阶段补齐 README 的完整目标。它们不作为前四个阶段交付最小可用能力的前置条件，各阶段仍按一个用户问题划分小版本。

### v4.x：历史重建与扩展

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v4.0 历史状态重建 | 指定时点的账户是什么状态？ | 从最近快照重放标准账户事实，查询覆盖范围内的持仓、成本和账户价值 | 回放与官方快照校验；无目标时点价格时返回数量或标注估值精度；结果可追溯 |
| v4.1 区间重算 | 数据补齐或规则更新后，分析能重新计算吗？ | 对受影响区间重算账户状态、盈亏和指标 | 重算范围和计算版本明确；相同事实与规则产生一致结果；历史修正不误触发跟单 |
| v4.2 更早历史补充 | 能分析观察开始之前的历史吗？ | 接入 Nansen 或适用的节点等补充来源，扩展历史分析范围 | 官方 API 保持 Hyperliquid 实时主源；来源去重和冲突处理明确；披露实际覆盖、估算和估值精度 |

### v5.x：多链与多协议扩展

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v5.0 新链或协议接入 | 能观察 Hyperliquid 之外的账户吗？ | 接入一个新链或协议，查询并持续获取标准账户事实 | 支持相应节点采集或第三方订阅；来源差异由适配器处理；区块连续性、检查点恢复和适用的确认语义明确 |
| v5.1 独立账户分析 | 新链或协议的账户表现怎样？ | 按链和协议独立建账，计算账户状态和指标 | 每个账本独立校验；计算口径、来源及覆盖清楚；不可比指标不混用 |
| v5.2 地址级聚合 | 同一地址的整体表现怎样？ | 聚合不同链和协议的账户价值与可比较指标 | 统一计价和资金流边界明确；不重复计算跨链资产及转移；披露覆盖和估算比例 |

### v6.x：数据完整审核

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v6.0 独立异步复核 | 已获取的数据是否存在缺口或异常？ | 查询缺失、重复、乱序、状态差异和适用的链重组异常 | 独立进程运行，不阻塞实时发布与跟单；复核范围和异常影响可见；无法自动处理时告警 |
| v6.1 多来源对账 | 不同来源的数据是否一致？ | 按需抽样或全量核对来源记录，定位差异 | 对账范围、来源身份和差异依据可追溯；主源异常时可按配置使用适用备用来源 |
| v6.2 修复闭环 | 发现问题后能修复并更新分析吗？ | 回补、修正或撤销记录，并更新受影响分析 | 通过修正事件传播变化，不静默覆盖；接入 v4.1 重算；修复后重新复核；历史修正默认不补单 |

### v7.x：钱包扩展

| 版本 | 主要问题 | 新增用户能力 | 验收边界 |
| --- | --- | --- | --- |
| v7.0 本地签名器 | 能使用本地签名方式吗？ | 在统一钱包接口下接入本地签名器 | 使用 KMS/HSM 或专用密钥服务保护密钥；请求身份、权限和调用记录可追溯 |
| v7.1 外部 MPC 钱包 | 能使用 MPC 钱包吗？ | 接入外部 MPC 钱包执行跟单 | 密钥按服务托管模型管理；仅保存钱包引用；完成签名、提交、超时恢复和结果核对 |
| v7.2 第三方托管钱包 | 能使用其他托管钱包吗？ | 接入第三方托管钱包 | 明确仅签名与签名并发送的能力差异；失败恢复和去重通过验收；新增适配不改变跟单规则 |

v3.x 先选择一种钱包实现跑通执行。v7.x 扩展钱包选择，已支持的路径可复用并直接验收，不重复建设。凭证保护是首次实盘执行的要求，不推迟到钱包扩展阶段。

## 7. 依赖与推进顺序

```text
程序基础：v0.0 → 后续所有版本沿用的工程、HTTP 与配置基础
交易采集：v0.0 → v0.1 → … → v0.7
账户分析：v0.4 → v1.0 → … → v1.7
筛选评价：基础分析及多地址能力 → v2.0 → … → v2.3
跟单执行：v0.5 → v3.0 → … → v3.4（可并行）
后续扩展：账户分析 → v4.x 历史重建与扩展
          统一账户事实与分析 → v5.x 多链与多协议
          采集与分析 → v6.x 完整审核（修复重算依赖 v4.1）
          统一钱包接口与跟单执行 → v7.x 钱包扩展
```

- 大版本号表示能力阶段，不强制串行等待。后续扩展按实际需求启动，审核需求明确时可以提前安排 v6.x。
- v0.4 的单地址持续采集稳定后，可以开始账户分析路线。现货相关分析依赖 v0.7；多账户比较依赖多地址能力。
- v0.5 的候选信号稳定后，可以开始跟单路线，与账户分析和筛选评价并行推进。
- 基础跟单不以完成综合评分、策略识别或历史重建为前提。需要按分析结果选择目标时，再接入对应能力。
- 跟单规则、风险限制和签名执行保持独立边界；数据完整审核交付时作为独立进程运行，不阻塞采集、事件发布和跟单；其他模块按实际规模安排进程拆分，保持各服务的数据归属和接口边界。
- 各阶段持续提供可查询的账户详情、历史变化、分析结果、审核状态或跟单记录；结果披露更新时间、覆盖范围和计算口径。

## 8. 迭代与完成原则

1. 当前版本详细设计，下一版明确范围，远期版本保留能力目标和验收边界。
2. 每版都有可使用入口和明确的能力边界；v0.0 验收配置、HTTP 请求与启动退出场景，业务版本使用实际地址或真实业务场景验收。
3. v0.0 建立 HTTP 服务和配置基础；后续按实际需要加入业务 API、数据库、部署工具、审核或多数据源，避免提前建设整套基础设施。
4. 保留必要的正确性要求：稳定身份、金额精度、错误可见、覆盖披露、来源追溯和凭证保护。
5. 数据与接口变更采用明确迁移或兼容方案；已有用户能力持续可用。
6. 每次发布后实际使用一轮，根据反馈调整、拆分或取消下一版；不以完成全部路线作为发布条件。
7. 所有版本的目录结构、模块职责和依赖方向遵循概要与详细设计，在已有程序基础上扩展；功能范围逐版增加，不为每个版本另起一套实现。
